# InfluxDB — Sensor Time-Series Source

ภาพรวมการใช้ **InfluxDB 2.x** ในสถาปัตยกรรม Unified IIoT ของเรา ตั้งแต่ schema, connector, ไปจนถึง ETL ลง Oracle DW

> **Last updated:** 2026-04-26
> **Source of truth:** [`influx_connection.py`](../db_module/db_conn/influxdb/influx_connection.py) + [`etl_influxdb_to_oracle.py`](../db_module/pipeline/airflow/dags/etl_influxdb_to_oracle.py)

---

## 1. Role ในสถาปัตยกรรม

InfluxDB เป็น **time-series source** สำหรับสัญญาณ sensor 1Hz ที่อ่านจาก 3 เครื่องในไลน์ Battery Assembly:

```
┌─────────────────────────────────────────────────────────────┐
│  Edge: Node-RED → MQTT → Telegraf → InfluxDB (AWS EC2)      │
└─────────────────────────────┬───────────────────────────────┘
                              │ Flux query (aggregateWindow 15m)
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Airflow DAG: etl_influxdb_to_oracle (schedule */15)        │
│  → Oracle STG_SENSOR_AGG (truncate-and-load)                │
└─────────────────────────────┬───────────────────────────────┘
                              │ SP_LOAD_FACT_SENSOR
                              ▼
                   Oracle FACT_SENSOR (Kimball star)
```

**ทำไมต้องมี InfluxDB:**
- Sensor signal 1Hz × 3 machines × 6 fields = ~518k point/วัน — ใส่ลง Oracle ตรง ๆ ทำ I/O ระเบิด
- InfluxDB optimize สำหรับ time-series compression + windowed aggregation (Flux `aggregateWindow`)
- เรา **ไม่เก็บ raw signal** ใน DW — DW เก็บแค่ aggregate 15-min (mean/min/max/count) ก็พอสำหรับ Kimball reporting

## 3. Schema (Bucket / Measurement / Tag / Fields)

### Bucket: `iiot_data_raw`

> ⚠️ มี **2 default ที่ขัดกัน** ในโค้ด — ต้องระวัง:
> - [`influx_connection.py:30`](../db_module/db_conn/influxdb/influx_connection.py#L30) → `INFLUX_BUCKET=sensors`
> - [`etl_influxdb_to_oracle.py:52`](../db_module/pipeline/airflow/dags/etl_influxdb_to_oracle.py#L52) → `INFLUX_BUCKET=iiot_data_raw`
> - [`.env.example`](../.env.example) → `INFLUX_BUCKET=sensors`
> - **README + production .env** ใช้ `iiot_data_raw` → **ค่าจริงในระบบคือ `iiot_data_raw`** (default ใน connector ผิดเก่า ควรแก้)

### Measurement: `station_1`

หนึ่ง measurement เก็บข้อมูลทั้งไลน์ (3 เครื่อง) แยกด้วย tag

### Tag: `machine_id`

| Tag value | หมายถึง |
|---|---|
| `M01` | เครื่องที่ 1 (formation) |
| `M02` | เครื่องที่ 2 (assembly) |
| `M03` | เครื่องที่ 3 (testing) |

ตัวอักษรต้องตรงกับ `DIM_MACHINE.machine_name` ใน Oracle เป๊ะ — ถ้าผิด case หรือ space ก็ JOIN ไม่เจอ → `FACT_SENSOR` จะ silent-empty

### Fields (6 metrics, 1Hz)

| Field | Unit | Owner machine (DIM_METRIC) |
|---|---|---|
| `temperature_c` | celsius | M01 |
| `machine_state_num` | binary (0/1) | NULL = ทุกเครื่อง |
| `cycle_count` | count | M02 |
| `vibration_g` | g-force | M02 |
| `current_a` | ampere | M03 |
| `voltage_v` | volt | M03 |

> **Note:** เครื่องไหน emit field ไหน ถูก seed ไว้ที่ [`DIM_METRIC` ใน 01_schema.sql:67-78](../db_module/db_sources/oracle_sql_query/query/01_schema.sql#L67-L78) — InfluxDB ไม่บังคับ schema นี้ (เครื่องอาจยิง field อื่น ๆ ได้) แต่ SP_LOAD_FACT_SENSOR กรองด้วย `DIM_METRIC.machine_name` ทำให้เฉพาะ tuple ที่ map เป็น dimension ได้เท่านั้นที่ลง FACT

### Sampling rate

- **1 Hz nominal** → ~900 sample ต่อ 15-min window ต่อ (machine × field)
- `sample_count` ใน `FACT_SENSOR` ใช้ flag sensor down ได้ — ถ้า count << 900 แปลว่า data missing

## 4. Connector — `InfluxConnector`

[`db_module/db_conn/influxdb/influx_connection.py`](../db_module/db_conn/influxdb/influx_connection.py)

Wrapper บาง ๆ บน `influxdb_client.InfluxDBClient`:

```python
from db_module.db_conn import InfluxConnector

influx = InfluxConnector()                    # อ่าน env: INFLUX_URL/ORG/TOKEN/BUCKET
tables = influx.query('from(bucket:"iiot_data_raw") |> range(start:-1h)')
```

### Public API

| Method | จุดประสงค์ |
|---|---|
| `__init__(url, org, token, bucket)` | Constructor — ถ้าไม่ส่ง args จะอ่านจาก env (URL/TOKEN = `require`, ORG/BUCKET มี default) |
| `client()` (`@contextmanager`) | Yield `InfluxDBClient` — ใช้เมื่อต้องเรียก API ที่ wrapper ไม่ได้ห่อ (เช่น `delete_api`, `write_api`) |
| `query(flux: str) -> list[FluxTable]` | Run Flux query แล้วคืน FluxTable ดิบ — ไม่ flatten เป็น DataFrame เพื่อให้ caller เข้าถึง groupKey/column types |

### Design notes

- **Stateless** — ทุก call เปิด-ปิด client ใหม่ใน context manager (ไม่ pool connection — query rate ต่ำพอ)
- **Fail-fast บน auth** — `URL` และ `TOKEN` ใช้ `require()` → throw ถ้าไม่มี env (ไม่ silent default)
- **`org` และ `bucket`** ใช้ `get(default)` → optional, มี fallback

> **ข้อสังเกต:** DAG `etl_influxdb_to_oracle.py` **ไม่ได้ใช้ `InfluxConnector`** — มันเรียก `InfluxDBClient` ตรง ๆ เพราะ DAG ไม่ import package ในเครื่อง (Airflow container path isolation) ใช้ env แทน

## 5. ETL Flow: InfluxDB → Oracle `STG_SENSOR_AGG`

### DAG: [`etl_influxdb_to_oracle.py`](../db_module/pipeline/airflow/dags/etl_influxdb_to_oracle.py)

| Property | Value |
|---|---|
| `dag_id` | `etl_influxdb_to_oracle` |
| `schedule` | `*/15 * * * *` (ทุก 15 นาที) |
| `data_interval` | 15-min window ตรงกับ Flux `aggregateWindow` |
| Tasks | `check_oracle_api` → `aggregate_sensor` |

### Flux query — 4 ครั้งต่อ window (mean / min / max / count)

```flux
from(bucket:"iiot_data_raw")
  |> range(start: ${data_interval_start}, stop: ${data_interval_end})
  |> filter(fn:(r) => r._measurement == "station_1")
  |> aggregateWindow(every: 15m, fn: ${mean|min|max|count}, createEmpty: false)
```

**ทำไมต้อง 4 query แยก:** Flux ไม่มี `aggregateWindow` ที่คำนวณ multi-aggregate ใน pass เดียว → ทำใน Python: เก็บผลลัพธ์ลง dict โดย key = `(machine_id, field, window_end)` แล้ว join

### Output: `STG_SENSOR_AGG` (Oracle)

1 row ต่อ `(machine × metric × 15-min window)`:

```
machine_name | metric_name      | window_start | window_end | avg | min | max | sample_count | src_system | pipeline_run_id
M01          | temperature_c    | 14:00        | 14:15      | ... | ... | ... | 900          | INFLUXDB   | <run_id>
M02          | vibration_g      | 14:00        | 14:15      | ... | ... | ... | 900          | INFLUXDB   | <run_id>
...
```

- **Max 18 row/รอบ** = 3 machines × 6 fields (จริงน้อยกว่า เพราะแต่ละเครื่อง emit field set ของตัวเอง)
- **Truncate-and-load** — STG = buffer ของ window ล่าสุด ไม่สะสม
- **Bridge:** insert ผ่าน FastAPI service (`bulk_insert` ใน `_oracle_api.py`) ไม่ใช่ JDBC ตรง — เพราะ Airflow container ไม่มี JVM

### Edge case ที่ต้องระวัง

| Case | Behavior |
|---|---|
| `INFLUX_URL` / `INFLUX_TOKEN` ไม่ set | DAG warn + skip task (ไม่ fail) — ใช้ตอน dev บน laptop ไม่มี cloud creds |
| Flux คืน 0 row | warn + return — ไม่ insert (truncate ไม่ทำงาน → STG ค้าง window ก่อนหน้า ⚠) |
| `min/max key` ไม่ match `mean key` | เก็บเป็น `NULL` (ห้าม fallback เป็น avg) — fix 2026-04-19 จากที่เคย silent-misleading |
| `aggregateWindow` ใส่ timestamp ที่ end | คำนวณ `window_start = win_end - 15min` |

## 6. Configuration (Environment Variables)

ตั้งใน `.env` ที่ root ของ repo (ดู [`.env.example`](../.env.example)):

```bash
INFLUX_URL=http://<ec2-public-ip>:8086
INFLUX_ORG=factory
INFLUX_BUCKET=iiot_data_raw           # ⚠ override default 'sensors' ของ connector
INFLUX_TOKEN=<from InfluxDB UI>
INFLUX_MEASUREMENT=station_1          # optional, DAG default
INFLUX_RANGE_START=                   # optional, สำหรับ ad-hoc backfill เช่น "-6h" หรือ ISO ts
```

### Backfill / Manual run

```bash
# ใน Airflow container, override window
docker compose -f $COMPOSE exec -T \
  -e INFLUX_RANGE_START=2026-04-18T04:00:00Z \
  airflow-scheduler airflow dags trigger etl_influxdb_to_oracle
```

## 8. Known Issues / TODO

| Issue | Detail |
|---|---|
| 🟡 Default bucket mismatch | `InfluxConnector` default `"sensors"` แต่ระบบจริงใช้ `"iiot_data_raw"` — ควร sync default |
| 🟡 DAG ไม่ใช้ `InfluxConnector` | DAG `etl_influxdb_to_oracle` open client เอง → DRY violation, ถ้าเปลี่ยน auth pattern ต้องแก้ 2 ที่ |
| 🟡 Hard-code `measurement="station_1"` | ถ้ามีไลน์ที่ 2 (`station_2`) ต้อง add DAG ใหม่ — หรือ abstract เป็น loop จาก DIM table |
| 🟡 STG ไม่ truncate ตอน Flux ว่าง | ถ้า Flux คืน 0 row, DAG return ก่อนเรียก `bulk_insert(truncate=True)` → STG ยัง hold window เก่า (อาจ load FACT ซ้ำ) |
| 🟡 Sensor down detection | ใช้ `sample_count` ใน FACT แต่ยังไม่มี alert/threshold |
