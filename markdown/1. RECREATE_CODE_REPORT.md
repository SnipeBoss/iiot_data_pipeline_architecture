## 5. Mock Window Logic

- **Principal cap:** 7 days from `latest`
- **Shift alignment:** ใช้ shift boundary แทน timestamp boundary เพื่อหลีกเลี่ยง partial shift
- **Trailing DAY shift:** เพิ่ม DAY-04-25 หลัง NIGHT-04-24 เพื่อให้ทุก calendar date ใน window มี DAY orders (ผ่าน 4.5.1 shift coverage check)

| Boundary | Value | Reason |
|---|---|---|
| `start_date` | `2026-04-18` | DAY-04-18 starts 07:30 > earliest 04:27 ✓ |
| `night_end_date` | `2026-04-24` | NIGHT-04-24 ends 04-25 06:30 < latest 04-26 04:04 ✓ |
| `day_end_date` | `2026-04-25` | DAY-04-25 ends 16:30 < latest 04-26 04:04 ✓ |

**Final shift schedule:** 8 DAY + 7 NIGHT = **15 shifts** (DAY-04-18 → NIGHT-04-24 → DAY-04-25)

## 8. Issues Encountered & Resolutions

### Issue 1 — File numbering mismatch ระหว่าง spec กับ filesystem
- **Spec เริ่มต้น:** `01_schema.sql` (รวม trigger), `02_master_data.sql`
- **Filesystem จริง:** `01_schema.sql`, `02_trigger_functions.sql`, `03_master_data.sql`
- **Resolution:** STOP + report กลับ user → user แก้ `RECREATE_CODE.md` ให้ตรงกับ filesystem (3 ไฟล์ใน query/, mock เป็น 04)

### Issue 2 — `apply_supabase.py` outdated paths + audit list
- `DEFAULT_FILES` ชี้ `02_master_data.sql` ที่ไม่มี + ขาด `02_trigger_functions.sql`
- `_AUDIT_TABLES` ยังอ้าง `"product"` table ที่ไม่มีใน schema ใหม่
- **Resolution:** Update ทั้งสอง constant ให้ตรง schema ปัจจุบัน

### Issue 3 — Yield ratio min=0.848 (< 0.85 spec floor)
- **Cause:** `round(qty_planned * yield_rate)` ปัดลงจน ratio ต่ำกว่า floor สำหรับ batch เล็ก เช่น `qty_planned=33, yield=0.85 → round(28.05)=28 → 0.848`
- **Resolution:** Clamp post-round ด้วย `math.ceil(qty_planned * 0.85)` เมื่อ ratio < 0.85
- **Result:** min ขยับเป็น 0.851 ✓

### Issue 4 — 04-25 calendar date มีแค่ NIGHT (ขาด DAY)
- **Cause:** Window เดิม end = NIGHT-04-24 (ends 04-25 06:30) → orders 04-25 มีแค่ post-midnight residual ของ NIGHT-04-24, ไม่มี DAY orders บน DATE 04-25
- **Resolution:** Split end date เป็น `night_end_date=04-24` + `day_end_date=04-25` → iter_shifts emit extra DAY-04-25 หลัง loop ปกติ
- **Result:** ทุก calendar date 04-18..04-25 มี DAY+NIGHT ครบ

### Issue 5 — production_order 105 below spec floor 110
- **Cause:** Stagger `randint(75, 90)` packed orders ห่างเกินไป → max ~7 DAY + ~10 NIGHT × 7 days = 119 ceiling, ในทางปฏิบัติได้ 105
- **Resolution:** ลด stagger เป็น `randint(70, 85)` + initial offset `randint(1, 5)` (จากเดิม 5–15)
- **Result:** 126 orders ✓

## 10. Trigger-Aware Insert Pattern (sanity check ผ่าน)

Generator ปฏิบัติตาม pattern ที่ trigger คาดหวัง:

```sql
-- 1) batch insert ด้วย status='CREATED', times=NULL, qty_out=already-set
INSERT INTO production_batch (batch_id, ..., status_code, qty_out, start_time, end_time)
VALUES (101, ..., 'CREATED', 72, NULL, NULL);

-- 2) events insert ตามลำดับเวลา → trigger trg_sync_batch_status update batch ทุก row
INSERT INTO batch_status_event (batch_id, status_code, reason_code, event_ts) VALUES
  (101, 'CREATED',   NULL,         '2026-04-22 11:45:00.000000'),
  (101, 'STARTED',   NULL,         '2026-04-22 11:50:00.000000'),
  (101, 'COMPLETED', NULL,         '2026-04-22 12:10:00.000000');
-- หลัง events 3 row ถูก insert → batch.status_code='COMPLETED', start=11:50, end=12:10
```

จุดที่ได้ระวัง:
- `qty_out` set ใน batch INSERT (ห้าม UPDATE ทีหลัง)
- `start_time/end_time` ของ batch ปล่อย NULL — trigger ใส่เอง
- `duration_min` ของ downtime ปล่อย NULL — trigger BEFORE INSERT ใส่เอง
- Microsecond uniqueness ภายใน batch (UNIQUE `uq_batch_event_ts`) — guard loop เพิ่ม `+1µs` หากชน
- Reason category match strictly:
  - `batch_status_event.reason_code` → `BATCH_HOLD` only (PAUSED ใช้ `LUNCH_BREAK`/`MATERIAL_SHORTAGE`)
  - `downtime_event.reason_code` → `MACHINE_DOWNTIME` only (`EQUIPMENT_FAULT`/`SENSOR_ALARM`/`POWER_OUTAGE` + `PLANNED_PM`)
